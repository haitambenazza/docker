Docker engine : is the software that run and manages the containers or simply refered as Docker
    and it's made from many components (The API, Image builder, High level runtime, Low level runtime)
    when the docker was released it was made of two major components:
        - docker deamon (dockerd): contains the code for the API, image builder, runtime and more...
        - LCX (linux container): set of tools that allowes you create System containers, combine namespaces and cgroups into
        one set. in another word docker engine hanlde high level stuff like API, image build while LXC handles the low level
        stuff like namespaces but after 2014 Docker replaces LXC with it's own library called libcontainer (part of runc) since
        LXC relies on linux based System

docker image: it's a read only package that has everything to build the app, they are made of stacked layers, those layers represent
    the minimal OS, the dependacies , the app code and the config file, you can also say that images are stopped containers.
    - usually they are stored in /var/lib/docker/
    - to check for images in the local host : "docker images" or "docker image ls"
    these images can be either built or pulled from registeries like DockerHub by running "docker pull <image>", also you can search
    an image using "docker search <image>", you can inspect and see the layers of an image while pulling or running "docker insepct <image>"
    deleting image:
        - to delete an image we use "docker rmi <image>", however if an container uses that image it will not be deleted
        - to delete all the images on a host "docker rmi $(docker images -q) -f"

docker container: if the image is the template or the 'class' then container is the instance, it's the runtime instance of an image
        - to start a container we run "docker run <image> <app/executable/script>" you can specify name with flag --name.
            the container will run untill the main app exits, or by stoping it by running "docker stop <container ID>"
            you can also remove a container by running "docker rm <container ID>"

        - so far we can define the container as next: container = Image(Read-only) + writtable Layer+ Isolated process
            and for the writtable layer if you stop the container or the process exited, all the data in that layer will be lost,
            that's why we need to write them into volume.
        - difference between container and VM machine:
            - as we used to do with VM, the VM machine needs a host machine and a hypervisor, when the hypervisor boots it claims
            all the CPU,RAM,storage... then turn these hardware thing into virtual constructs (hardware virtualization), but for
            the containers is a different stroy , instead of doing hardware virtualization, they do OS virtualization by claiming
            process tree, filesystem, network stacks... while the OS of the host machine is the one handling the hardware resources
            not another prgram like hypervisor.
        - self-healing container policies:
            - always: always restart failing containers if they aren't expicitly stopped by running "docker run --restart always"
                or by declare it in yaml file to be used by higher level tools like docker compose
            - unless-stopped: in this mode the if the docker service got restarted unlike the always , the container will not start
            - on-failure : it will restart the container if it exited with a non zero code or when the docker service restarted

OCI (Open Container Initiative) is set of rules that describe how should containers and images be build
    3 main rules of OCI:
        - image specs: it define what should be inside a container image file
            - Manifest: a JSON file listing configs and layers
            - The Layers: Tarballs of the actual filesystem changes
            - The configs: a JSON file containing the env variables and the commands to run
        - the runtime specs: this defines how should a container started and managed
        - distribution specs: this describes how should images be pushed and pulled from registeries like DockerHub

The OCI workflow
    - docker run nginx (docker engine or deamon finds the requested image by docker CLI)
    - docker then tells containerD to handle the lifecycle, containerD pulls the The OCI image and pack it
    into OCI bundle (a folder in the disk)
    - containerD calls runc to initiate the container
    - runc reads the config.json from The OCI bundle then makes the syscalls needed to create namespaces the cgroups

- containerD is a high-level runtime , it takes abstracted commands from docker (by Docker CLI) and turn them into OCI bundle for runc
    also it's the one that manage and monitor the running containers
    containerd has 3 responsabilities:
        - Image management: handles push and pull, communicate with registeries like DockerHub, download layers and store them into the disk
        - Monitoring: it manages the "Union Filesystem" ,it's reads the layers from an image (Read-only),stack them on each and then add a
        writable layer if the process tries to make a new file or to edit an existed one.
        - Execute runc: after preparing the layers, it run "runc", once runc exists the containerd leave a small process called shim to keep
        watching the running container and report if it crashes or existed with an error code.
        - Metadata: keep tracking the containers ,which one is running, their IDs, which image they're using.

- runc is a standalone CLI to run the containers according to OCI runtime specs by calling a set of syscalls (clone(), pivot_root()...)
    to transfrom the standard process into container (or isolated process)
    workflow of runc:
        - Read the config file: parse config.json to see which namespaces requested(PID, Network, Mount...).
        - Create namespaces: uses unshare() to run the program in a new namespaces and clone() syscall to abstracts
        the process from the rest (basically assigning PID 1).
        - setup Cgroups: writes new PID into cgroups.proc file a new created control blocks, basically handcuffing the process
        - remove the permissions: basically removes and strips down any previlidged commands or root power.
        - Exec : finally it replaces itself with the actual command you wanted to execute.
    it is possibile to go very low and run the "runc" command without docker or containerd.

- cgroups are a kernel feature that allows you to allocate resources like tasks (CPU,RAM,GPU...)

- containerization
    - containerization is about build, ship and run the end to end process and it can be done as next:
        - create the app and dependacies
        - create a Dockerfile to describe how to build the app and run it
        - build it into image running "docker build image-name <build context>"
        - run the container form the image
    -Dockerfile : a plain text file that tells docker how to build an app into image by a set of instructions, it is a good pratice to keep
        the Dockerfile in the build context (dir that hold the srcs).
        - Dockerfile filesystem creators (creates layers):
            - FROM : this instruction will pull the specified image and use it as base layer.
            - COPY: takes files from the host machine and copy them into the image.
            - ADD: same as COPY, but can add files from URLs or auto-extract .tar files into the image.
            - RUN: creates a temporary container to run the specified command, and adds it to a new Read-only layer.
        - Dockerfile Metadata setter(edits the image config JSON at runtime):
            - WORKDIR: Sets the the specified dir as current dir for any subsequence of RUN,COPY,ENTRYPOINT...
            - ENV: sets the env variables and inject them into the process env
            - EXPOSE: this is only for documentation, it doesn't open any port, but just expicitly telling the user what port
                is expected to be opened.
            - USER: a command to change permissions and UID before running a process , basically setting a default user for the
                container
            - VOLUME: declare a specified directory as mount point, by marking it to be in the writable layer.
        - Dockerfile execution directives:
            - ENTRYPOINT: this will be the first binary that runc will exec, the process will become PID 1.
            - CMD: the argument for ENTRYPOINT.
    - multi container:
        - when trying to deploy and manage lot of microservices using only docker, it will takes lot of scripting and longer docker
            commands, that's why we use docker compose in one config file.
        - docker compose: a client-side tool that run and manage the containers (like Makefile), why should we use it?
            well for many reasons rather than speeding up the deploying process, in inception Wordpress depends on mariadb
            if Wordpress started before mariadb which might results on crash, for that compose uses a dependicy graph (depends_on)
            to handle the order of execution of the containers, also in docker networking , when we want to connect containers with each other
            we need manually run docker network create and each time before starting the container we need to specify the network
            but with compose all these problems get solved.
        - docker-compose.yaml: is a config file that tells how to build and run each service, a service may contian more than one
            container.
            - it has 3 major components:
                - services: each entry in the services defines how to configure and run the service, when you run <up> it send a POST
                    request to the docker engine API to create isolated PID namespaces
                    - build: instead of pulling a pre-made image ,it called dockerfile specified in <dockerfile: path> from a context build
                        specified in <context: path>
                    - container_name: assign a name to the container
                    - image: assign a name to the resulted image , if it doesn't exists docker builds it.
                    - restart: defines the behavior when the process exits (always)
                    - env_file: Points to the .env , docker reads the file and inject the password into the enviroment namespaces.
                    - ports: <Host port: container port>
                    - depends_on: defines order of execution
                - networks: this section defines the virtual connection between the services.
                    - driver: <bridge> tells the kernel to create a Linux bridge (virtual switch), all the containers in this
                        network will get their own IP in a private network.
                    - netwoks: (inside services) to plug a service in a specific port , you can put all the containers in virtual
                        netwok and expose only the wanted service by giving it a port.
                - volumes: link the temporary filesystem with local VM's disk.
                    - driver: <local> tells docker to use local filesystem
                    - driver_opt:
                        - type: <none> don't use any special filesystem like NFS
                        - device : <path> absolute path on VM host.
                        - o: <bind> bind mount to staple the VM host folder in the container namespace.
        docker compose commands:
            docker compose up : it will read and parse the yaml file, use the dockerfiles to build images and start containers
            docker compose stop: stop the containers and networks, won't delete them (SIGTERM)
            docker compose down: stop the containers and networks and will delete them (make fclean)
        docker volumes:
            - volume: is presistence layer that we can use to store the data and not loosing it after removing the containers,
                their seperated from containers.
            - docker volume create: we can create a volume with this command but we might need to specify more flags
                or simply specify it while running a container, --mount source=<vol>,target=<path in container>
